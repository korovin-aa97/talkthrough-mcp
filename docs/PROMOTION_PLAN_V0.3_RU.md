## Коротко: что именно мы будем делать

Мы не будем пытаться ежедневно публиковать посты и комментарии от имени автора.
Вместо этого мы:

1. Подготовим один очень понятный пример: человек записывает баг, а Talkthrough
   превращает запись в доказательства и готовый материал для coding agent.
2. Бесплатно подадим Talkthrough в официальные каталоги плагинов и инструментов.
3. Предложим Talkthrough редакции рассылки о developer tools для независимого обзора.
4. Купим несколько размещений в двух небольших, но очень подходящих рассылках для
   разработчиков, которые используют AI в работе.
5. Разнесём размещения по времени, чтобы Talkthrough попадался разработчикам несколько
   раз в течение 4–6 недель, а не исчез после одного дня запуска.
6. После каждого этапа посмотрим на реальные переходы и реакции. Оставшиеся деньги
   потратим только в том случае, если первые размещения работают.

## 1. Что будет считаться победой

С бюджетом $500–700 невозможно гарантированно «купить вирусность». Платные размещения
могут привести первых правильных пользователей. Настоящее распространение начинается,
когда эти пользователи сами применяют Talkthrough в работе и показывают результат своей
команде.

### Главная цель

За 6 недель после v0.3 получить **не меньше 10 подтверждённых пользователей**, которые
действительно обработали хотя бы одну запись, а не просто открыли GitHub.

Поскольку Talkthrough не собирает телеметрию, подтверждением может быть:

- вопрос или issue от пользователя;
- сообщение в GitHub Discussion;
- добровольно присланный пример результата;
- независимое упоминание или обзор;
- прямой ответ пользователя, что он успешно обработал запись.

### Хороший результат кампании

- 150–300 целевых переходов на GitHub или страницу демо;
- 20–40 новых GitHub stars;
- 10 подтверждённых первых запусков;
- 5 или больше содержательных вопросов, issues или предложений;
- хотя бы одно независимое упоминание Talkthrough не самим автором;
- стоимость одного целевого перехода не выше $4.

### Очень хороший результат

- 50 или больше новых stars;
- 20 или больше подтверждённых пользователей;
- сторонний автор сам делает видео, статью или пример использования;
- появляется второй поток посетителей, который уже не зависит от купленной рекламы.

Stars и загрузки PyPI — вспомогательные показатели. Они полезны, но не доказывают, что
человек успешно воспользовался продуктом.

## 4. Что должно быть готово до начала продвижения

Не начинать платную кампанию в тот же день, когда код v0.3 только считается готовым.
Сначала провести отдельную проверку релизной версии.

### 4.1. Выбрать одну главную историю

Не рекламировать список новых функций v0.3. Человек должен за 10–15 секунд понять один
результат:

> Don't write a bug report. Record it. Talkthrough превращает локальную запись бага в
> расшифровку, точные кадры, OCR и доказательства, с которыми Claude Code или Codex может
> подготовить issue или исследовать исправление.

Новые функции v0.3 нужно показывать только как доказательство того, что эта история стала
надёжнее или полезнее.

### 4.2. Записать новое настоящее демо

Требования к демонстрации:

- длительность 60–90 секунд;
- реальный запуск v0.3 без монтажа, скрывающего ожидание или ошибки;
- понятный баг, который видно на экране;
- короткое голосовое объяснение проблемы;
- в конце виден полезный результат агента;
- отдельно сказано, что запись не загружается в сервис Talkthrough;
- никаких секретов, токенов и личных данных в кадре;
- пример можно повторить по файлам из репозитория.

Нужно сохранить две версии:

1. Полное видео со звуком для YouTube и README.
2. Короткий GIF или ролик 15–25 секунд без обязательного звука для каталогов.

### 4.3. Подготовить единый «пакет запуска»

Все площадки должны получать одни и те же проверенные материалы. Это уменьшит ручную
работу и не даст обещаниям расходиться.

Папка или документ с материалами должен содержать:

- название: `Talkthrough`;
- однострочный слоган;
- описание на 50–70 слов;
- описание на 120–150 слов;
- квадратный логотип;
- изображение 1200×630 для карточек и ссылок;
- 2–3 понятных изображения «запись → доказательства → результат»;
- ссылку на 60–90-секундное видео;
- ссылку на GitHub;
- одну основную команду установки;
- список поддерживаемых клиентов;
- короткое объяснение privacy;
- честный список ограничений;
- email для связи.

### 4.4. Проверить первый опыт нового пользователя

Попросить человека или чистого агента, который раньше не устанавливал Talkthrough,
выполнить путь с нуля:

1. Открыть GitHub.
2. Понять назначение инструмента.
3. Установить его по одной из основных инструкций.
4. Обработать короткую тестовую запись.
5. Получить понятный результат.

Кампания не должна начинаться, если:

- инструкция требует догадок;
- основная команда установки не работает;
- первая обработка регулярно падает;
- пользователь не понимает, где найти результат;
- реальное поведение расходится с обещанием в рекламе;
- README сначала показывает много технических деталей и только потом объясняет пользу.

### 4.5. Подготовить доверие

Talkthrough обрабатывает потенциально чувствительные записи экрана. Перед рекламой нужно,
чтобы новый пользователь быстро увидел:

- открытый исходный код и MIT license;
- понятное объяснение, что выполняется локально;
- отсутствие runtime-телеметрии;
- перечень разовых загрузок моделей и инструментов;
- опубликованные результаты CI;
- provenance/attestation опубликованных пакетов;
- SECURITY.md или понятный способ сообщить об уязвимости;
- честные ограничения Windows и других платформ;
- свежий changelog v0.3.

OpenSSF Scorecard workflow подключён 26 августа 2026 года. Он еженедельно проверяет
практики supply-chain security и публикует результаты в GitHub Security и OpenSSF API.
Первый успешный запуск дал 6,1/10. При этом проект уже получил 10/10 за CI, SAST,
проверку уязвимостей, закреплённые зависимости, минимальные права workflow, Dependabot,
лицензию и отсутствие бинарных файлов. Оценку сейчас снижают главным образом молодой
возраст репозитория, сольный процесс без обязательного одобрения PR, отсутствие fuzzing и
неподписанные GitHub-релизы. Прямая ссылка на private vulnerability reporting и генерация
подписанного provenance уже настроены; новый provenance появится в assets следующего
GitHub-релиза. Публичный badge лучше добавить ближе к v0.3, после повторного Scorecard scan
по новому релизу.

### 4.6. Не покупать GitHub stars

Покупка stars не входит в этот план ни при каком результате кампании.

GitHub прямо запрещает неаутентичные взаимодействия, автоматическое выставление stars,
злоупотребление рейтингами и участие в рынках неаутентичной активности. Нарушение может
привести к удалению активности, ограничению или блокировке аккаунта.

Даже если не учитывать правила, купленные stars вредят именно Talkthrough:

- опытные разработчики замечают новые пустые аккаунты и неестественный резкий скачок;
- большое число stars без forks, issues, обсуждений и реальных пользователей выглядит
  подозрительнее, чем честный молодой проект;
- редактор или автор рассылки может отказаться рекомендовать проект;
- после покупки невозможно понять, дала ли настоящая кампания органический рост;
- фальшивые stars не устанавливают продукт, не дают feedback и не показывают его коллегам;
- для local-first продукта подделка публичного показателя особенно сильно бьёт по доверию.

Безопасные способы сделать проект солиднее:

1. Показать настоящее короткое демо без скрытого монтажа.
2. Сделать установку и первый результат предсказуемыми.
3. Показывать CI, package provenance, security policy и воспроизводимые benchmarks.
4. Публиковать настоящие отзывы только с разрешения их авторов.
5. После успешного использования ненавязчиво написать: «If Talkthrough helped, a GitHub
   star helps other developers discover it». Не давать за star подарок, деньги или доступ.
6. Считать более важными реальные первые запуски, issues и независимые упоминания.

Честные 20–30 stars у нового узкого developer tool выглядят лучше, чем 300 stars без
следов реального использования.

## 10. Контрольные точки и решения

### После первого платного письма

#### Зелёный сигнал

- 30+ уникальных переходов;
- 3+ новых stars;
- хотя бы один реальный вопрос, запуск или содержательная реакция.

**Действие:** продолжать план и оплачивать второй newsletter.

#### Жёлтый сигнал

- 15–29 переходов;
- 1–2 stars;
- нет подтверждённого запуска.

**Действие:** не паниковать и не покупать больше рекламы. Проверить, понятны ли первые

#### Красный сигнал

- меньше 15 переходов;
- нет содержательных реакций;
- площадка не даёт отчёт.

**Действие:** остановить необязательные расходы, не оплачивать второй newsletter и не
трогать резерв. Сначала выяснить, проблема в аудитории, тексте, демо или установке.

### После трёх размещений основной рассылки

#### Кампания работает

- 100+ переходов суммарно;
- 10+ новых stars;
- 3+ подтверждённых первых запуска;
- стоимость перехода до $3–4.

**Действие:** можно потратить часть резерва на повтор лучшего канала.

#### Кампания дала только внимание

- переходы есть, но никто не устанавливает и не задаёт вопросов.

**Действие:** проблема, вероятно, не в охвате, а в странице, установке или ценности первого
сценария. Не покупать ещё охват до исправления конверсии.

#### Кампания не дала внимания

- мало переходов даже при подтверждённых открытиях письма.

**Действие:** проблема в сообщении или несовпадении аудитории. Сохранить резерв для другой

## 12. Как создать распространение внутри самого продукта

Платная реклама заканчивается вместе с бюджетом. Чтобы Talkthrough продолжал
распространяться, результат его работы должен естественно показывать ценность другим
разработчикам.

До v0.3 или сразу после него стоит рассмотреть отдельный **явно выбранный пользователем**
режим shareable report. В такой отчёт можно добавить небольшую честную строку:

> Prepared locally from a screen recording with Talkthrough — the recording was never
> uploaded.

Эта строка может содержать ссылку на GitHub или короткое демо. Тогда готовый issue в
GitHub, Linear или Jira увидят другие участники команды. Это и есть потенциальная вирусная
петля:

1. Один разработчик устанавливает Talkthrough.
2. Создаёт хороший отчёт о баге.
3. Коллеги видят не рекламу, а полезный результат.
4. Один из коллег пробует Talkthrough для следующего бага.

Важно:

- не добавлять скрытую подпись без ведома пользователя;
- не загружать отчёт или запись куда-либо автоматически;
- не превращать профессиональный issue в рекламный баннер;
- оставить простой способ убрать подпись;
- подчёркивать local-first, потому что это отличает Talkthrough от облачных записывающих
  сервисов.

## 13. Чего не делать

### Не покупать

- GitHub stars;
- Product Hunt upvotes;
- готовые комментарии от подставных аккаунтов;
- «гарантированное первое место» в launch-каталоге;
- безымянные пакеты из сотен backlinks;
- широкую рекламу для всех интересующихся AI;
- рекламу с минимальным бюджетом, который не позволяет провести нормальный тест.

Покупные GitHub stars отдельно запрещены правилами GitHub о spam and inauthentic activity:
там прямо перечислены fake accounts, automated starring, rank abuse и вторичные рынки
неаутентичной активности.

### Не запускать всё в один день

Одновременный запуск создаёт красивый график, но не показывает, какой канал сработал. Через
два дня внимание исчезает, а повторного контакта с продуктом нет.

### Не обещать больше, чем делает v0.3

Особенно опасны формулировки:

- «Talkthrough автоматически исправляет любой баг»;
- «полностью понимает любое видео»;
- «не использует сеть вообще», если при первом запуске скачиваются модели;
- «поддерживает платформу», если она не прошла реальную проверку;
- «официальный Claude/Codex plugin», пока plugin не принят в официальный каталог.

### Не менять всё после слабого результата

Если одновременно заменить аудиторию, заголовок, GIF, CTA и README, невозможно понять,
что помогло. Между размещениями менять только один главный элемент.
